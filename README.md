# Diamond Price Prediction and Value Segmentation

An end-to-end data science pipeline: exploratory analysis, price regression,
value-segment classification, and unsupervised clustering, served through a
Next.js dashboard that runs the models in the browser.

Built on the `ggplot2` diamonds dataset (53,940 raw rows). All numbers quoted
anywhere in this repo are regenerated by `train.py`; nothing is hard-coded.

**Live:** https://diamond-pricing.vercel.app

## Headline results

| Task | Model | Metric |
|---|---|---|
| Price regression | Random Forest | R2 0.9824, MAE $262, RMSE $523 |
| Price regression (baseline) | Linear Regression | R2 0.9153, MAE $777, RMSE $1,147 |
| Value segmentation | Random Forest classifier | 93.34% accuracy, 0.933 weighted F1 |
| Value segmentation (baseline) | Logistic Regression | 91.02% accuracy, 0.910 weighted F1 |
| Clustering | K-means, k=2 | silhouette 0.351 |

80/20 train/test split, seed 42, 10,755 held-out rows.

## The finding that matters

Carat dominates price, but the interesting part is what happens to the quality
grades once size is held constant. Splitting the data into carat quintiles and
comparing price per carat within each band shows the grades behave differently:

| Grade | Smallest quintile | Largest quintile | Direction |
|---|---|---|---|
| Cut (Fair vs Ideal) | 96% | 71% | premium widens with size |
| Clarity (I1 vs IF) | 50% | 37% | premium widens with size |
| Colour (J vs D) | 59% | 71% | premium narrows with size |

Clarity is worth roughly 2x at the bottom of the market and about 2.7x at the
top. Colour is the most predictable of the three, holding near 1.4x across
every size band. A single sourcing rule applied uniformly across all sizes is
wrong in three different directions.

## Why there are two models

The models reported in the results table and the model running in your browser
are not the same object, and the difference is deliberate.

The full-precision pipeline trains unbounded-depth forests. That regressor
scores R2 0.9824 with a MAE of $262, and it serialises to **631 MB**. GitHub
refuses files over 100 MB and Vercel caps a serverless bundle at 250 MB, so
neither can host it. Hosting it anywhere else would need roughly 2 GB of RAM
just to unpickle, which no free tier provides.

So `export_web.py` retrains a depth-capped forest for deployment. Measured on
the identical split:

| | Full pipeline | Deployed in browser |
|---|---|---|
| Regression R2 | 0.9824 | 0.9808 |
| Regression MAE | $262 | $292 |
| Classifier accuracy | 93.34% | 91.35% |
| Size | 787 MB | 9.4 MB |

80 trees capped at depth 10 keeps the accuracy to within 0.002 R2 while being
66x smaller, which is small enough to ship as JSON and walk in JavaScript. A
random forest is just tree traversal, so no Python process is needed at all.

The dashboard labels which is which. The results table reports the full
pipeline's held-out metrics; the live predictor and the walkthrough run the
deployed model. `api.py` still serves the full-precision models locally.

The model binaries are gitignored. `train.py` rebuilds them from
`data/diamonds.csv` in a few minutes, and `export_web.py` writes the browser
copy.

The dense scatter plots use `hexbin` on log axes rather than 50k alpha-blended
markers, which render as a solid block. Charts are drawn on a light ground and
the dashboard gives them a deliberate plate in both colour schemes, so there is
one set of PNGs instead of two, and no second training run purely for dark
variants.

## Deployment

The site is fully static. `npm run build` prerenders the single page and the
models ship as files in `public/`, so there is no backend, no cold start and
no environment variable to configure. The model JSON is fetched lazily only
when the predictor or the walkthrough is opened.

```bash
./.venv/Scripts/python.exe train.py        # full pipeline + artifacts
./.venv/Scripts/python.exe export_web.py   # browser model + static assets
cd web && npm run build                    # prerender
```

To deploy: push to GitHub and import the repository in Vercel, setting the
root directory to `web`. Nothing else is required.

## Design

The interface follows an editorial field-guide language: cream paper against
deep aubergine panels, one peach accent, Space Grotesk for display, DM Sans for
reading, and monospace for every label and number. Sections are numbered
`01 / 07`. Light mode is a true inversion rather than a dimmed variant.

Both colour schemes are checked by machine:

```bash
.venv/Scripts/python.exe verify_contrast.py
```

Small-text tokens tuned for the dark ground are unreadable on cream. The
peach accent measures 2.38:1 on paper, which is why light mode uses a deeper
tone for anything the reader has to read.

## Running it

Two processes. Python serves the models, Next.js serves the UI.

```bash
# 1. train (about 4 minutes on a laptop, writes artifacts/)
.venv/Scripts/python.exe train.py

# 2. model server
.venv/Scripts/python.exe -m uvicorn api:app --port 8000

# 3. dashboard, in a second terminal
cd web
npm install
npm run dev
```

Open http://localhost:3000. The page degrades to an explanatory state if the
Python server is down, rather than erroring.

## Verifying the claims

`verify_copy.py` checks every factual statement in the dashboard copy against
`artifacts/dashboard_data.json`, including the direction of each grade effect,
the cluster agreement rate, and the confusion matrix structure. Run it after
any change to the pipeline or the UI copy:

```bash
.venv/Scripts/python.exe verify_copy.py
```

It is not a test suite that can silently pass. A claim that drifts out of sync
with the data is a failure, and this is what caught five of them during the
build.

## Design and interpretation notes

These are deliberate choices, not oversights:

**Ordinal encoding, not one-hot.** Cut, colour and clarity are ordered grades.
One-hot encoding would throw the ranking away and let a tree learn five
unrelated categories.

**Price is excluded from the classifier.** The segment labels are derived from
price, so including price as a feature would be leakage. The classifier has to
infer the tier from physical and quality attributes alone, which is why 93%
rather than 100% is the interesting number.

**Feature importance is reported by group, not per column.** Carat, log carat,
volume, x and y correlate at 0.999. A tree can move the credit for one signal
between those columns arbitrarily, so per-column rankings split one number five
ways. Grouping them by what a buyer actually controls is the honest version.
The per-column numbers are still written to `artifacts/feature_importance.csv`.

**Clusters are compared against the labels, not merged with them.** K-means sees
size and proportion only. It agrees with the price quartiles on about half the
stones, and that disagreement is the result worth reporting rather than a
defect to paper over.

## Limitations

The dataset is a public sample of past transactions with no date, brand,
certification or market conditions attached. The model is least accurate on the
largest stones, where residuals fan out. Treat it as evidence about how weight
and grade relate to price, not as a valuation tool.
